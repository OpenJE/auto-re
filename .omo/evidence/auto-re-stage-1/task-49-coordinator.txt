Task 49: Implement durable coordinator loop with no-progress detection + completion-policy gate
Date: 2026-07-22

## What was done
- Created `autore-reconstruction/src/coordinator/` module:
  - `mod.rs` — `Coordinator` struct with async `tick()` implementing spec §14.1 phases in order:
    reconcile_interrupted_operations → refresh_provider_health → refresh_program_structure_if_requested
    → update_work_dependencies → invalidate_stale_work → promote_ready_work → select_ready_work.
  - `state.rs` — `CoordinatorState`, `CoordinatorWorkItem`, `ProviderHealth`, response-hash history.
  - `policy.rs` — `CompletionPolicy` (terminal = Completed/Blocked/Cancelled; Blocked is not success),
    `NoProgressDetector` with last-3 identical raw-response-hash tracking.
  - `handlers.rs` — `WorkKindHandlers` trait with seven dispatch methods, `DispatchKind` classifier
    mapping the schema-level `WorkItemKind` to StaticInvestigation / DynamicInvestigation /
    SemanticAnalysis / ConflictResolution / Generation / BuildFailure / Verification.
  - `tests.rs` — unit tests for dispatch, no-progress blocking, cancellation, reconciliation, and
    completion policy.
- Re-exported coordinator types from `autore-reconstruction/src/lib.rs`.
- All tick outputs route through `ApplicationCommand`, preserving the atomic-import-per-iteration
  invariant.

## Design decisions
- `Investigation` work items are disambiguated by description prefix (`static:`, `dynamic:`,
  `semantic:`) because the schema-level `WorkItemKind` enum does not yet contain the fine-grained
  sub-kinds referenced in the task description.
- Completion policy distinguishes `is_complete` (all required terminal) from
  `is_successfully_complete` (no blocked required items remain).
- No-progress blocking emits `BlockWorkItem` with reason tag
  `RepeatedIdenticalModelOutput:<DispatchKind>`.
