# auto-re-stage-0 - Work Plan

## TL;DR (For humans)

**What you'll get:** A durable, observable foundation for the auto-re platform: persistent projects with stable, sortable identities; immutable content-addressed artifacts; canonical entities independent of any provider; complete provenance for all observations and hypotheses with append-only history; explicit contradictions; generic verification records; long-running operations with structured progress and cooperative cancellation; every state change committed atomically alongside a durable project event with monotonic per-project ordering; replayable events with no-gap live subscriptions; a shared application command/query layer that both CLI and the existing Ratatui TUI use; a forward V1→V2 schema migration with rollback safety; project-wide validation; and rebuildable derived indexes. A project can be created, inspected, modified, validated, migrated, closed, reopened, and watched live — all without any IDA, Ghidra, debugger, or LLM running.

**Why this approach:** The repo already shipped a Milestone-1 prototype (Campaign/Task/Claim/Evidence domain + mock scheduler/worker + a 4-panel Ratatui dashboard + SQLite). Stage 0 supersedes that domain but must not throw away the Ratatui widgets, terminal lifecycle, kill→resume guarantee, or working toolchain — so the plan first pins current TUI behavior with regression tests, then remaps it onto the new Stage 0 model, and ports the kill→resume guarantee as durable Operation state plus atomic state-plus-event commits plus sequence-gap recovery. Three irreversible choices were answered up front: a full seven-crate workspace split (so CLI and TUI are compile-time barred from touching SQLite), UUIDv7 for sortable stable identities, and an aggressive domain replacement that defers the M1 analysis/model/scheduler/worker/engine code to a non-default member crate for reuse in Stage 1.

**What it will NOT do:** No reverse-engineering analysis of any kind (no IDA/Ghidra/Binary Ninja, no disassembly/decompilation, no CFG/call-graph, no type inference, no LLM, no debugger, no symbolic/sandbox execution, no source generation, no LSP, no automatic provider alignment or contradiction detection or confidence calculation or hypothesis auto-acceptance). No network transport. No plugin UI runtime. No multiple storage backends.

**Effort:** XL
**Risk:** Medium-high — the seven-crate workspace split touches every existing path, and the atomic state-plus-event transaction plus V1→V2 migration rollback are the load-bearing correctness claims; a regression baseline is captured first to protect the existing terminal experience.
**Decisions to sanity-check:** full 7-crate workspace split with `autore-stage1` kept off the default build/test path (`default-members` exclusion + explicit `--exclude autore-stage1` for spec §32 #44/#46 `--workspace`-scoped commands); UUIDv7 over the existing `uuid` crate (v7 feature); aggressive M1 domain replacement; SHA-256 default content hash with BLAKE3 retained for V1 backward compatibility; in-process `tokio::sync::broadcast` for live events (`EVENT_BROADCAST_CAPACITY = 256`); SQLite + refinery retained; `expectrl` (with portable-pty fallback) for the pseudo-terminal TUI test; `cargo clippy --workspace --exclude autore-stage1 --all-targets -- -D warnings` and `cargo fmt --all --check` as final hardening gates.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- Do NOT perform any reverse-engineering analysis: no IDA/Ghidra/Binary Ninja, no disassembly/decompilation, no CFG/call-graph/SCC, no machine IR, no semantic function bodies, no type inference, no LLM/`llama_cpp`, no debugger/`gdbstub`, no symbolic/sandbox execution, no source/LSP, no automatic entity alignment, no automatic contradiction detection from provider output, no automatic confidence calculation, no automatic hypothesis acceptance.
- Do NOT put `autore-stage1` on the default `cargo build`/`cargo test` path — `default-members` in the workspace Cargo.toml excludes it.
- Do NOT let `IDAError` (or any provider-specific error) into the `autore-core::Error` type.
- Do NOT use SQLite AUTOINCREMENT / DEFAULT uuid() / rowid as public IDs (lint-enforced).
- Do NOT mutate the original Evidence row to erase history — append-only lifecycle events only.
- Do NOT let TUI hold authoritative state, do NOT import `rusqlite` in `autore-tui`, do NOT let TUI execute raw SQL or directly mutate records or kill provider processes.
- Do NOT pass raw JSON command payloads through the internal application interface — explicit tagged `ApplicationCommand`/`ApplicationQuery` only.
- Do NOT use timestamps for event ordering — project-local monotonic sequence numbers, in-transaction.
- Do NOT make Stage 0 implement Operation *execution* / scheduler leasing / worker dispatch — only Operation records + state transitions + progress + cooperative cancellation requests (Stage 1).
- Do NOT derive anything beyond Stage 0 derived indexes (counts/aggregates/caches) during rebuild — no model routing derivations.
- Do NOT integrate a network transport or remote coordinator — `LocalAutoReClient` only.
- Do NOT support arbitrary native TUI plugins; a generic fallback renderer suffices.
- Do NOT split serialization shapes across Rust enum defaults — explicit tagged forms via `#[serde(tag="kind", content="value")]`.

## Commit strategy
- One atomic conventional commit per todo (`feat`/`test`/`build`/`fix`/`docs`/`chore` as appropriate), in dependency order.
- Commit message format: `<type>(<scope>): <imperative summary>`.
- Scope matches the crate the change lives in (`schema`/`core`/`store`/`app`/`events`/`cli`/`tui`/`workspace`/`stage0`/`store`/etc.).
- No commit ever leaves a default-members workspace in a non-compiling state — `cargo build` (default-members) must pass before each commit.
- Migrations are.versioned per Phase but land atomically with the record-type todo that introduces them (do not commit a migration without the Schema record it depends on).
- The V1 fixture file `tests/fixtures/v1_project.sqlite3` lands in task 35 with a `tests/fixtures/README.md` documenting its generation procedure.
- Stage 0 audit + final report (`docs/stage0-*.md`) land in tasks 3 and 39 respectively.
- Do not squash until the final verification wave passes; keep history granular for review.
- Final verification wave commits use `fix(<scope>): ...` for any corrections.
